# Русские блины

Рабочий демонстрационный desktop-прототип для Windows: прогноз спроса, сверка запасов и редактируемая заявка на пополнение. Интерфейс на русском языке. Все вычисления, база и Excel-экспорт работают локально, без сервера.

Оформление «КРОНА»: бордовый `#A4002A`, тёмный текст `#111E30`, белые поверхности и светлые розовые состояния из презентации. Встроен шрифт Inter. Экран остатков содержит таблицу и отдельную область поставки, а заявка — вкладки ингредиентов и прогноза. Подробности визуальной системы находятся в `DESIGN.md`. Ctrl+K переводит фокус в поиск, Ctrl+1…5 переключают разделы.

С 27.10.2026: отмена последней правки черновика с журналом, восстановление рабочего места между запусками, боковая карточка ингредиента, поиск действий по Ctrl+Shift+P, уведомления с открытием файла/папки, сравнение сохранённых заявок и крупный режим. Для просмотра на отдельной сохраняемой демо-базе — `start_interaction_demo.cmd`; инструкция — [INTERACTION_FEATURES.md](INTERACTION_FEATURES.md).

Основные разделы «Остатки» и «Спрос» переключаются сверху, а боковое меню меняется вместе с выбранным разделом. При первом запуске приложение открывается на обзоре запасов; далее восстанавливается последнее рабочее место точки. В «Остатках» доступны дела на сегодня, заявка, история и данные остатков; в «Спросе» — продажи и прогноз, сравнение месяцев, наличие блюд, пилот и данные продаж. Фильтры, выбранное блюдо и ручные правки не сбрасываются при переходах. Настройки точки доступны внизу боковой панели.

Прежние интерактивные графики сохранены: продажи и прогноз, покрытие потребности запасами и доли блюд в продажах. Доступны периоды 14/30/90 дней, сравнение трёх завершённых месяцев и разворачивание главного графика. Нажатие на блюдо в круговой диаграмме выбирает его динамику; на ингредиент — открывает расчёт. При небольшом окне графики доступны через прокрутку.

В шапке показаны имя для журнала и выбранная точка. Контекст точки задаётся в настройках и сохраняется между запусками; это не механизм авторизации. График поставок относится только к выбранной точке: при его отсутствии расчёт блокируется, а для добавления нужно явно отметить «График для этой точки задан» и проверить дату/интервал. Реальный вход оператора терминала ещё не подключён.

В окне изменения упаковки, целевого запаса и резерва причину можно выбрать из списка или написать свою. Последние использованные причины предлагаются повторно; выбранная или введённая причина записывается в журнал вместе с изменением параметров.

Профиль справа в шапке содержит круг с инициалами, имя, точку и терминал. Имя берётся из поля для журнала; «Название терминала» задаётся в настройках, а при пустом значении показывается имя компьютера. Длинные подписи сокращаются, полный текст доступен в подсказке.

## Запуск

Сборка от 28.10.2026 включает все изменения интерфейса, шесть рабочих функций и семь улучшений взаимодействия. Для запуска достаточно одного `dist/RusskieBliny.exe`; отдельные Python, библиотеки и папка `assets` не нужны. Проверки и контрольная сумма — [RELEASE_2026-10-28.md](RELEASE_2026-10-28.md) и [release-manifest.json](release-manifest.json).

Откройте `RusskieBliny.exe` в папке `dist`. Python устанавливать не требуется. При первом запуске автоматически создаются **явно помеченные синтетические данные** за последние 12 месяцев относительно даты первого запуска.

База: `%LOCALAPPDATA%\RusskieBliny\data.sqlite3`. Черновики, исходные рекомендации, подтверждения и журнал сохраняются между запусками. В «Настройках» можно создать проверенную резервную копию открытой базы, включая изменения из WAL, и восстановить её. Перед восстановлением текущая база автоматически сохраняется в подпапке `backups`. Демо-база не сбрасывается при повторном запуске. Для изолированной демонстрации можно запустить `RusskieBliny.exe --data-dir ДРУГАЯ_ПАПКА`.

По умолчанию расчёт использует сегодняшний день. При наступлении нового дня приложение обновляет дату и требует пересчёта и повторной сверки для неподтверждённых заявок; ручные правки сохраняются. Для исторического расчёта снимите «Всегда использовать сегодняшнюю дату» в настройках. Ручная дата явно показывается в шапке. Прошедшая дата поставки блокирует расчёт с предложением проверить график: неподтверждённое будущее поступление автоматически не выдумывается.

Если график отсутствует или дата поставки прошла, сохранённые фактические остатки всё равно отображаются. Карточка показывает количество, подтверждённую пригодность и время сверки; расчётные показатели остаются незаполненными. Фильтры пополнения/излишка временно недоступны. При восстановлении раздела заявки с недоступным расчётом приложение открывает остатки; сам черновик, ручные количества и причины сохраняются. Для расчёта новой заявки укажите согласованную дату в «Настроить поставки».

«Сохранить настройки» проверяет ближайшую поставку относительно выбранной даты расчёта **до записи**. Прошедшая дата или период более 90 дней отклоняются с указанием поля; остальные изменения формы также не записываются. Поле «Ближайшая поставка» находится выше параметров модели. После корректного сохранения открываются обновлённые остатки либо график спроса, существующий неподтверждённый черновик пересчитывается с сохранением ручных количеств и причин. Перед подтверждением нужна повторная сверка. Подтверждённые заявки не пересчитываются. Если график намеренно отключён или в данных есть ошибки, уведомление объясняет ограничение и не сообщает о готовом прогнозе.

## Основной сценарий

«Шаблоны XLSX / CSV» сохраняет пустые формы: их нужно заполнить до импорта. Для проверки загрузки выберите «Демо-пример» и импортируйте полученный `demo.xlsx`. При совпадении имён экспорт создаёт отдельную подпапку и сообщает путь в уведомлении; существующие файлы сохраняются. Пустой XLSX и пустой справочник точек отклоняются без изменения базы.

1. На экране «Данные и импорт» загрузите полный XLSX по шаблону. Сначала можно пройти сценарий на предзагруженных демонстрационных данных.
2. В «Обзоре» проверьте динамику и дату закрытых смен. Переключитесь на «Остатки» для сверки: там показаны дата последней закрытой смены и время импорта. Двойной щелчок раскрывает расчёт конкретного ингредиента.
3. «Сверить / списать»: выберите партию, задайте фактическое количество или списание, подтвердите пригодность и укажите причину. Изменение попадет в журнал.
4. «Сформировать заявку»: проверьте период покрытия, рекомендации в упаковках и предупреждения справа. Прогноз порций находится на вкладке «Прогноз блюд».
5. Выберите строку → «Изменить количество» или двойной щелчок. Допустим нулевой заказ. Предпросмотр показывает стоимость и разницу к рекомендации, расчётный конечный остаток и непокрытую потребность. Изменение применяется после ввода причины и сохранения. При ошибке форма сохраняет ввод. Кнопка «Вернуть рекомендацию» также регистрирует изменение.
6. Отметьте сверку остатков и пригодности, нажмите «Подтвердить и сохранить», выберите файл Excel. Подтвержденная заявка сохраняется в базе. Отправка поставщику не выполняется.
7. После подтверждения состав заявки зафиксирован, кнопка предлагает повторный экспорт того же номера. «Новая заявка» создаёт отдельный черновик. В «Истории» можно найти заявку по номеру/дате, открыть состав и сохранённый прогноз, экспортировать её. История заявок ограничена выбранной точкой; общий журнал действий показывает автора, причину и понятные сведения «было → стало». Пересчёт неподтверждённого черновика сохраняет ручные количества отдельно от новой рекомендации.

В «Обзоре» доступен график «Запас по дням»: сравнение сценариев без нового заказа и с выбранным количеством. Кнопка «График запаса» в таблице открывает нужный ингредиент. Форма сверки также открывает партии выбранного ингредиента. График учитывает подтверждённые поступления, расход по действующей техкарте и только явно заданные даты использования партий. Непокрытая потребность отмечена точками; физический остаток не становится отрицательным. Поступления считаются доступными с начала дня. Это расчёт по исходному снимку, а не фактическое получение заказа. Количества неподтверждённого предпросмотра не меняют базу.

В ручной правке доступен список готовых причин: большой заказ, повышенный/сниженный спрос, дополнительный запас, перемещение с другой точки, изменение графика, ограничение места хранения и возврат к рекомендации. Поле остаётся редактируемым. Последние восемь использованных причин сохраняются между запусками, отдельно для заявки и сверки остатков. Причина не подставляется без выбора сотрудника. Ctrl+Enter сохраняет форму. В старом расчёте без данных графика доступна кнопка пересчёта с сохранением правок; незаписанные изменения требуют причины. Подсказки обычных элементов появляются через 100 мс без анимации; графики показывают значения сразу при движении указателя.

Если экспорт невозможен, подтвержденная заявка остается в истории и ее можно экспортировать повторно. Если изменены данные или настройки, подтверждение старого черновика блокируется до пересчета и повторной сверки. При удалении позиции с ручной правкой расчёт блокируется для выяснения сопоставления.

## Импорт

Дополнительные рабочие сценарии: **«Дела на сегодня»**, отдельный расчёт **«Что, если…»**, предпросмотр обновлений с разбором конфликтов, журнал наличия блюд, отчёт пилота и четыре демонстрационные ситуации. Запуск на свежей демо-базе — `start_customer_demo.cmd`. Порядок показа и ограничения — [OPERATOR_FEATURES.md](OPERATOR_FEATURES.md).

В `templates` находятся пустой XLSX и CSV всех восьми наборов; в `examples` — заполненный демонстрационный пример. Их также можно сохранить из интерфейса. Полное описание колонок — в `DATA_FORMAT.md`.

Файл импорта — **полный снимок затронутых таблиц**, а не добавление строк. В интерфейсе перед применением доступны сравнение с последним источником и разбор конфликтов с ручными правками. Локальные изменения, которых источник не менял, сохраняются; конфликт требует выбора строки и причины. Низкоуровневый `Store.import_file` сохраняет прежнюю замену таблиц и используется для первоначального демо-импорта. Для повторной загрузки идентичного файла используется SHA-256. Ссылки, обязательные значения, дубликаты, даты, единицы и числа проверяются до записи; при изменении данных после предпросмотра обновление блокируется.

Первый импорт очищает демонстрационные наборы и черновики. Реальные и демонстрационные данные не смешиваются. При CSV начните с `points`, затем `items`, далее зависимые таблицы. Удобнее первый раз загрузить полный XLSX. Журнал прошлой демонстрации и подтвержденные заявки сохраняются; в экспортированных заявках указан признак ДЕМО.

Нулевые продажи требуют явной строки с `qty=0`. Пропущенный день не считается нулем. Продажи открытой и текущей смены не импортируются в MVP; последняя подтвержденная смена — не позднее вчерашнего дня. Факт текущего наличия вводится отдельно.

## Демо обмена с ДАЛИОН

В разделе данных доступна кнопка «Демо обмена с ДАЛИОН». Модуль получает снимок от локального HTTP-имитатора, проверяет восемь наборов данных и открывает отдельную демо-базу в обычном интерфейсе для анализа и расчёта заявки. Можно проверить отсутствие связи и повторное получение без потери правок. Все данные синтетические; формат сервиса придуман для примера, подключения к реальной 1С нет.

Отдельный запуск: `start_dalion_demo.cmd` или `.\.venv\Scripts\python.exe dalion_demo.py`. Подробности, границы и проверки — [DALION_DEMO.md](DALION_DEMO.md).

## Прогноз и заявка

Обучение ограничено последними 12 календарными месяцами перед датой расчета. Более ранние записи не используются. Для каждой точки и блюда сравниваются:

- простое среднее как контрольная модель;
- последние восемь аналогичных дней недели;
- экспоненциальное взвешивание свежих наблюдений, коэффициент 0,9;
- сглаженная вероятность ненулевого спроса и размер ненулевой покупки (подход TSB, коэффициент 0,15).

Техническое предложение для сегментации: регулярный спрос при продажах не менее чем в 60% наблюдаемых доступных дней. Порог и окно свежих наблюдений настраиваются. Для регулярного спроса выбирается день недели или свежий спрос, для редкого — метод редкого спроса или свежий спрос, по меньшей MAE. При менее 28 доступных наблюдениях применяется явный ручной резерв из настроек блюда.

Методы сравниваются на последних 28 доступных днях с расширяющимся обучением только на прошлом. Выбор метода и показанные ошибки используют одно окно: это предварительная диагностика, для независимой оценки нужен отдельный пилотный период. Дни отсутствия товара исключаются из оценки спроса; потерянные продажи не оцениваются как измеренный факт. Акции не моделируются, поскольку данных нет. Диапазон: ожидаемый спрос ± стандартное отклонение свежих наблюдений × √число дней, снизу ограничен нулём. Это описательный ориентир с допущением независимости дней, без утверждения о 95% вероятности.

Период покрытия: от начала даты расчёта включительно до даты ближайшей поставки плюс интервал поставок, не включая конечную дату. Поставки и потребление агрегированы по дням; приход считается доступным с начала дня. Время внутри дня MVP не моделирует. Прошедший график блокирует расчёт. Рекомендация для ингредиента:

`ceil(max(0, потребление за весь период + целевой остаток − пригодный запас − подтвержденные поступления в периоде) / размер упаковки)`.

Расход до доставки уже входит в весь период и повторно не вычитается. Недостаток до поступления и разрывы из-за позднего прихода подсвечиваются отдельно: стандартный заказ не может задним числом устранить дефицит. Просроченные ожидаемые поступления не засчитываются. Упаковка и лишний запас от округления показаны отдельно. Общий ингредиент суммируется по всем блюдам один раз. Целевой запас трактуется как остаток к концу периода — **демонстрационное допущение для согласования**, второго страхового запаса нет.

Литры и килограммы не конвертируются. Тесто 0,12 л/порция и тара 5 л — только демо-настройки техкарты. Если расход ингредиента на разные блюда одинаков, показывается эквивалент в порциях; иначе — «разный расход». Доступные порции разных блюд не складываются.

## Пригодность и списания

Приложение не определяет пригодность, срок хранения блюда или дату порчи. В демо даты партий неизвестны и не подставляются. Продавец подтверждает пригодность по существующему процессу и может исключить партию.

Если **в исходных данных явно задана** дата `use_before` для партии, она используется как дополнительное ограничение планового использования: запасы расходуются по ближайшей известной дате, неиспользованная часть после указанной даты не уменьшает заявку. Дата включительна; она не вычисляется из поступления. Это позволяет проверить сценарий «часть запаса не будет использована до заданной даты» без выдуманного норматива. Неизвестная дата остается неизвестной и сопровождается предупреждением.

История списаний за 28 дней показывается в количестве и по текущей себестоимости из справочника, для ручной проверки избыточного запаса. Автоматическая подгонка спроса под списания не выполняется. Фактический снимок остатков не пересчитывается повторно на движения. Исправления и списания в интерфейсе сразу изменяют фактический снимок и пишутся в отдельный журнал с автором, временем и причиной. Журнал движения не заменяет полноценный бухгалтерский учёт.

## Офлайн и ограничения

Все возможности MVP доступны без интернета: просмотр, импорт локальных файлов, новый прогноз, правки, история и Excel. Переключатель «Режим без связи» демонстрирует это состояние и не притворяется проверкой модема. Автоматической синхронизации нет, поэтому конфликты с удаленным сервером не скрываются. Локальное изменение ревизии блокирует подтверждение устаревшего расчёта.

Версии, API и форматы Frontol/ДАЛИОН не подтверждены. Реализован контракт `AccountingAdapter` и файловый `FileAdapter`; прямого подключения к этим системам нет. Приложение однопользовательское, без удалённого кабинета, авторизации и разграничения прав. Имя автора задается вручную. Не запускайте несколько экземпляров с одной базой одновременно. Для промышленного режима необходимы роли, политика автоматических резервных копий, согласованная синхронизация, лимиты входных файлов и сопровождение. Защита повторного подтверждения действует на уровне SQLite и сохраняется после перезапуска; ошибка Excel не отменяет сохранённую заявку.

## Разработка и проверки

Python 3.13, PySide6 6.12, SQLite из стандартной библиотеки, openpyxl. Qt выбран для настоящего оконного Windows-приложения; SQLite — для транзакционного локального хранения. Ссылки на документацию: [Qt for Python](https://doc.qt.io/qtforpython-6/), [sqlite3](https://docs.python.org/3.13/library/sqlite3.html).

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe app.py
```

Проверки и сборка:

```powershell
.\.venv\Scripts\python.exe -m pip install pytest pyinstaller
.\.venv\Scripts\python.exe -m pytest -q --junitxml=qa/test-results.xml
.\.venv\Scripts\python.exe app.py --data-dir qa/data --smoke qa/screens
.\.venv\Scripts\python.exe build.py
```

Проверены регулярный/редкий спрос, 12-месячное окно, отсутствие будущих данных, известные и неизвестные даты партий, общий ингредиент, округление тары, ручные правки и перезапуск, предыдущая закрытая смена, дубли импорта, ошибки единиц и пропуски, отсутствие техкарты и остатка, сохранение и Excel, конфликт ревизий и локальный расчёт при недоступной сети. Снимки пяти экранов проверены визуально. См. `qa/verification.json` и `PILOT.md`.

Для перехода к реальным точкам нужны образцы выгрузок и версии учетных систем, актуальные техкарты и коэффициенты, подтвержденные остатки/пригодность, графики поставок, упаковки, поставки в пути и согласованная трактовка неснижаемого остатка.
