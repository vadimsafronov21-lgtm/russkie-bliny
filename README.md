# Русские блины

Рабочий демонстрационный desktop-прототип для Windows: прогноз спроса, сверка запасов и редактируемая заявка на пополнение. Интерфейс на русском языке. Все вычисления, база и Excel-экспорт работают локально, без сервера.

Оформление «КРОНА»: бордовый `#A4002A`, тёмный текст `#111E30`, белые поверхности и светлые розовые состояния из презентации. Встроен шрифт Inter. Экран остатков содержит таблицу и отдельную область поставки, а заявка — вкладки ингредиентов и прогноза. Подробности визуальной системы находятся в `DESIGN.md`. Ctrl+K переводит фокус в поиск, Ctrl+1…5 переключают разделы.

## Запуск

Откройте `RusskieBliny.exe` в папке `dist`. Python устанавливать не требуется. При первом запуске автоматически создаются **явно помеченные синтетические данные** за последние 12 месяцев относительно даты первого запуска.

База: `%LOCALAPPDATA%\RusskieBliny\data.sqlite3`. Черновики, исходные рекомендации, подтверждения и журнал сохраняются между запусками. Для резервной копии закройте приложение и скопируйте эту папку. Демо-база не сбрасывается при повторном запуске; дату и график при необходимости обновите в настройках. Для изолированной демонстрации можно запустить `RusskieBliny.exe --data-dir ДРУГАЯ_ПАПКА`.

## Основной сценарий

1. На экране «Данные и импорт» загрузите полный XLSX по шаблону. Сначала можно пройти сценарий на предзагруженных демонстрационных данных.
2. В «Остатках» проверьте дату последней закрытой смены и время импорта. Двойной щелчок раскрывает расчёт конкретного ингредиента.
3. «Сверить / списать»: выберите партию, задайте фактическое количество или списание, подтвердите пригодность и укажите причину. Изменение попадет в журнал.
4. «Сформировать заявку»: проверьте период покрытия, рекомендации в упаковках и предупреждения справа. Прогноз порций находится на вкладке «Прогноз блюд».
5. Выберите строку → «Изменить количество» или двойной щелчок. Допустим нулевой заказ. Укажите причину правки. Кнопка «Вернуть рекомендацию» также регистрирует изменение.
6. Отметьте сверку остатков и пригодности, нажмите «Подтвердить и сохранить», выберите файл Excel. Подтвержденная заявка сохраняется в базе. Отправка поставщику не выполняется.
7. В «Истории» доступны повторный экспорт и подробности каждого изменения. Пересчёт сохраняет ручные количества отдельно от новой рекомендации. Предыдущие версии расчёта доступны в журнале.

Если экспорт невозможен, подтвержденная заявка остается в истории и ее можно экспортировать повторно. Если изменены данные или настройки, подтверждение старого черновика блокируется до пересчета и повторной сверки. При удалении позиции с ручной правкой расчёт блокируется для выяснения сопоставления.

## Импорт

В `templates` находятся пустой XLSX и CSV всех восьми наборов; в `examples` — заполненный демонстрационный пример. Их также можно сохранить из интерфейса. Полное описание колонок — в `DATA_FORMAT.md`.

Каждый импорт — **замена затронутой таблицы целиком**, а не добавление строк. В файле должен быть весь нужный актуальный снимок соответствующего набора. Это явно указано в интерфейсе. Для повторной загрузки идентичного файла используется SHA-256, поэтому операции не удваиваются. Ссылки между таблицами, обязательные значения, дубликаты, даты, единицы и числовые ограничения проверяются до транзакции.

Первый импорт очищает демонстрационные наборы и черновики. Реальные и демонстрационные данные не смешиваются. При CSV начните с `points`, затем `items`, далее зависимые таблицы. Удобнее первый раз загрузить полный XLSX. Журнал прошлой демонстрации и подтвержденные заявки сохраняются; в экспортированных заявках указан признак ДЕМО.

Нулевые продажи требуют явной строки с `qty=0`. Пропущенный день не считается нулем. Продажи открытой и текущей смены не импортируются в MVP; последняя подтвержденная смена — не позднее вчерашнего дня. Факт текущего наличия вводится отдельно.

## Прогноз и заявка

Обучение ограничено последними 12 календарными месяцами перед датой расчета. Более ранние записи не используются. Для каждой точки и блюда сравниваются:

- простое среднее как контрольная модель;
- последние восемь аналогичных дней недели;
- экспоненциальное взвешивание свежих наблюдений, коэффициент 0,9;
- сглаженная вероятность ненулевого спроса и размер ненулевой покупки (подход TSB, коэффициент 0,15).

Техническое предложение для сегментации: регулярный спрос при продажах не менее чем в 60% наблюдаемых доступных дней. Порог и окно свежих наблюдений настраиваются. Для регулярного спроса выбирается день недели или свежий спрос, для редкого — метод редкого спроса или свежий спрос, по меньшей MAE. При менее 28 доступных наблюдениях применяется явный ручной резерв из настроек блюда.

Методы сравниваются на последних 28 доступных днях с расширяющимся обучением только на прошлом. Выбор метода и показанные ошибки используют одно окно: это предварительная диагностика, для независимой оценки нужен отдельный пилотный период. Дни отсутствия товара исключаются из оценки спроса; потерянные продажи не оцениваются как измеренный факт. Акции не моделируются, поскольку данных нет. Диапазон: ожидаемый спрос ± стандартное отклонение свежих наблюдений × √число дней, снизу ограничен нулём. Это описательный ориентир с допущением независимости дней, без утверждения о 95% вероятности.

Период покрытия: от начала даты расчёта включительно до даты ближайшей поставки плюс интервал поставок, не включая конечную дату. Поставки и потребление агрегированы по дням; приход считается доступным с начала дня. Время внутри дня MVP не моделирует. Прошедший график блокирует расчёт. Рекомендация для ингредиента:

`ceil(max(0, потребление за весь период + целевой остаток − пригодный запас − подтвержденные поступления в периоде) / размер упаковки)`.

Расход до доставки уже входит в весь период и повторно не вычитается. Недостаток до поступления и разрывы из-за позднего прихода подсвечиваются отдельно: стандартный заказ не может задним числом устранить дефицит. Просроченные ожидаемые поступления не засчитываются. Упаковка и лишний запас от округления показаны отдельно. Общий ингредиент суммируется по всем блюдам один раз. Целевой запас трактуется как остаток к концу периода — **демонстрационное допущение для согласования**, второго страхового запаса нет.

Литры и килограммы не конвертируются. Тесто 0,12 л/порция и тара 5 л — только демо-настройки техкарты. Если расход ингредиента на разные блюда одинаков, показывается эквивалент в порциях; иначе — «разный расход». Доступные порции разных блюд не складываются.

## Пригодность и списания

Приложение не определяет пригодность, срок хранения блюда или дату порчи. В демо даты партий неизвестны и не подставляются. Продавец подтверждает пригодность по существующему процессу и может исключить партию.

Если **в исходных данных явно задана** дата `use_before` для партии, она используется как дополнительное ограничение планового использования: запасы расходуются по ближайшей известной дате, неиспользованная часть после указанной даты не уменьшает заявку. Дата включительна; она не вычисляется из поступления. Это позволяет проверить сценарий «часть запаса не будет использована до заданной даты» без выдуманного норматива. Неизвестная дата остается неизвестной и сопровождается предупреждением.

История списаний за 28 дней показывается в количестве и по текущей себестоимости из справочника, для ручной проверки избыточного запаса. Автоматическая подгонка спроса под списания не выполняется. Фактический снимок остатков не пересчитывается повторно на движения. Исправления и списания в интерфейсе сразу изменяют фактический снимок и пишутся в отдельный журнал с автором, временем и причиной. Журнал движения не заменяет полноценный бухгалтерский учёт.

## Офлайн и ограничения

Все возможности MVP доступны без интернета: просмотр, импорт локальных файлов, новый прогноз, правки, история и Excel. Переключатель «Режим без связи» демонстрирует это состояние и не притворяется проверкой модема. Автоматической синхронизации нет, поэтому конфликты с удаленным сервером не скрываются. Локальное изменение ревизии блокирует подтверждение устаревшего расчёта.

Версии, API и форматы Frontol/ДАЛИОН не подтверждены. Реализован контракт `AccountingAdapter` и файловый `FileAdapter`; прямого подключения к этим системам нет. Приложение однопользовательское, без удалённого кабинета, авторизации и разграничения прав. Имя автора задается вручную. Не запускайте несколько экземпляров с одной базой одновременно. Для промышленного режима необходимы роли, резервное копирование, согласованная синхронизация, лимиты входных файлов и сопровождение.

## Разработка и проверки

Python 3.13, PySide6 6.12, SQLite из стандартной библиотеки, openpyxl. Qt выбран для настоящего оконного Windows-приложения; SQLite — для транзакционного локального хранения. Ссылки на документацию: [Qt for Python](https://doc.qt.io/qtforpython-6/), [sqlite3](https://docs.python.org/3.13/library/sqlite3.html).

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe app.py
```

Проверки и сборка:

```powershell
.\.venv\Scripts\python.exe -m pip install pytest pyinstaller
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe app.py --data-dir qa/data --smoke qa/screens
.\.venv\Scripts\python.exe build.py
```

Проверены регулярный/редкий спрос, 12-месячное окно, отсутствие будущих данных, известные и неизвестные даты партий, общий ингредиент, округление тары, ручные правки и перезапуск, предыдущая закрытая смена, дубли импорта, ошибки единиц и пропуски, отсутствие техкарты и остатка, сохранение и Excel, конфликт ревизий и локальный расчёт при недоступной сети. Снимки пяти экранов проверены визуально. См. `qa/verification.json` и `PILOT.md`.

Для перехода к реальным точкам нужны образцы выгрузок и версии учетных систем, актуальные техкарты и коэффициенты, подтвержденные остатки/пригодность, графики поставок, упаковки, поставки в пути и согласованная трактовка неснижаемого остатка.
