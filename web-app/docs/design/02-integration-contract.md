# Предлагаемый контракт интеграции с 1С

Версия предложения: `rb.integration.v1-draft`. Это контракт между нашим backend и **согласованным интеграционным сервисом**, не существующий API заказчика. Машиночитаемая OpenAPI/JSON Schema и контрактные fixtures — результат этапа 1 после проверки терминов. Примеры ниже полностью демонстрационные.

**Уточнение по ответам команды:** реального сервиса, тестовой базы и разработчика 1С нет, заказчик данные не предоставляет. Этот документ — будущая граница интеграции и основа изолированного demo-теста. Обязательный шестинедельный MVP ведёт собственный журнал приложения по внутренним накладным и приёмкам; он не зависит от получения доступа к 1С. Не нужно реализовывать все ресурсы контракта до работающего MVP.

## 1. Ответственность сторон

1С остаётся источником подтверждённых справочников и учётных фактов. Наш backend читает их, сохраняет оригиналы и нормализованную копию, ведёт прогнозы и внутренние заявки. Кладовщик вручную создаёт документы в 1С. Прямых SQL-записей в 1С нет. Автоматический черновик документа — отдельный будущий контракт с отдельным разрешением.

Платформа 1С описывает стандартный REST/OData и его публикацию, но это не подтверждает наличие публикации, прав или нужных объектов в базе заказчика: [официальный REST-интерфейс 1С](https://v8.1c.ru/platforma/rest-interfeys/). API-ключи нашего контракта не предполагаются штатной возможностью этого интерфейса.

Варианты после обследования:

- Согласованный HTTP-сервис/расширение 1С, реализующий ограниченную выгрузку и журнал изменений; API-ключ проверяет этот сервис либо шлюз перед ним.
- Шлюз к доступному OData/другому разрешённому механизму. Он преобразует поля в наши схемы и использует отдельную учётную запись 1С с правами чтения. Шлюз не может восстановить потерянные исторические рецептуры или доказать включение продажи в остаток, если исходных связей нет.
- Для учебной работы — demo-адаптер с тем же контрактом. Пакетные выгрузки могут стать временным вариантом реального чтения, но без журнала и связей ограничивают актуальность и оперативный учёт.

Необходимые работы у заказчика при отсутствии готового сервиса: согласовать mapping; опубликовать доступ; ограничить права; определить семантику проведения/отмены/перепроведения; обеспечить стабильные ID и версии; экспорт снимка согласованного среза; журнал изменений и удаления; связь движений с физическими операциями и состав включённых эффектов; тестовые сценарии. Оценка трудоёмкости возможна после обследования. Если эти изменения недоступны, включается режим подтверждённых снимков без смешения с оперативным ledger.

## 2. Транспорт, ключи, общие правила

- HTTPS с проверкой сертификата. Пример адреса — `https://integration.example.invalid/rb/v1`; домен `.invalid` не обозначает работающий сервер.
- Заголовки: `Authorization: ApiKey <secret>`, `X-Request-ID`, `Accept: application/json`. Ключ не в URL. Backend и шлюз редактируют/удаляют секретные заголовки до логирования.
- Ключ имеет ID, разрешённый source/point/warehouse scope, read scopes (`catalog:read`, `sales:read`, `inventory:read`, `changes:read`), срок действия, revoked_at. Применяется принцип минимальных прав. Разные ключи для demo/test/prod и разных потребителей.
- Ротация: выпустить новый ключ, обновить серверный secret, проверить соединение, отозвать старый после ограниченного перекрытия. При компрометации отзыв немедленный. Отзыв проверяется на каждом запросе; кэш решения ограничен и инвалидируется.
- Шлюз хранит отдельные исходящие учётные данные 1С; scopes нашего ключа не заменяют права учётной записи в 1С. Ограничения IP/VPN возможны дополнительно, по среде заказчика.
- `schema_version` имеет major; добавление необязательных полей совместимо, изменение значения/обязательности требует новой major. Неизвестный критичный тип/версия — карантин, не молчаливое принятие.
- Время ISO 8601 с часовым поясом, хранение UTC. Отдельно `occurred_at`, `source_recorded_at`, `exported_at`, локальное `received_at`. День продажи — timezone точки, а не сервера.
- ID — opaque string; название не ID. Количество — decimal string и unit ID; деньги — decimal string + currency. `null` значит неизвестно/не предоставляется, 0 — известный ноль. Необязательность объявляется capabilities.
- Все примеры и тестовые сообщения имеют `data_mode: demo`. Production не принимает demo-поток без отдельного тестового окружения.

## 3. Ресурсы и capabilities

| Метод и путь | Результат и ограничения |
|---|---|
| `GET /capabilities` | schema/source generation, доступные datasets, поддержка snapshot coverage, история, retention журнала, limits, scopes, optional fields |
| `GET /bootstrap` | Дескриптор неизменяемой первоначальной выгрузки: export_id, consistency_token, boundary_cursor, список ресурсов и контрольные суммы; получение не создаёт учётных документов |
| `GET /exports/{export_id}/{dataset}?page_token=...&limit=...` | Страница согласованной выгрузки, opaque next_page_token, checksum, consistent scope; курсор не меняет содержимое страниц |
| `GET /changes?cursor=...&limit=...` | Упорядоченная страница at-least-once изменений, next_cursor, server_time; cursor привязан к источнику, поколению, фильтру и scope ключа |
| `GET /stock-snapshots/{snapshot_id}` | Метаданные неизменяемого снимка, scope, as_of, completeness, consistency revision, coverage mode и ссылки на страницы |
| `GET /stock-snapshots/{snapshot_id}/lines?page_token=...` | Полный набор строк снимка с единицами, партиями и отдельно резервами |
| `GET /stock-snapshots/{snapshot_id}/coverage?page_token=...` | Какие канонические эффекты, версии и signed quantities включены в снимок, включая частичное проведение |
| `GET /health` | Состояние сервиса без секретов; не заменяет контроль полноты синхронизации |

`dataset`: points, warehouses, units, conversions, menu_items, ingredients, recipe_versions, sales, cancellations, refunds, stock_snapshots, movements, receipts, transfers, writeoffs, inventories; при наличии — menu_availability, prices, promotions, lots, expiries. Поступления/списания/перемещения дают семантику документов, а физические изменения объединяются в **один** ledger эффектов, не суммируются дважды. Перемещение — парные строки расхода и прихода по разным местам с единым transfer_id; товар в пути не является остатком точки.

Минимальная декларация возможностей:

```json
{
  "schema_version": "rb.integration.v1-draft",
  "data_mode": "demo",
  "source_system": "demo-1c",
  "source_generation": "demo-gen-1",
  "datasets": ["points", "ingredients", "recipe_versions", "sales", "movements", "stock_snapshots"],
  "snapshot_coverage": "explicit_effect_quantities",
  "change_delivery": "at_least_once",
  "revision_semantics": "full_entity_state",
  "supports_tombstones": true,
  "optional_fields": {"lot_expiry": true, "ingredient_cost": false},
  "journal_retention_days": 30,
  "max_page_size": 500
}
```

30 дней и 500 строк — параметры только демонстрационного контракта, не заявленные возможности 1С. Для согласованного среза поставщик должен удерживать стабильный экспорт либо обеспечить повторяемое чтение и boundary журнала. Если это невозможно, первоначальная загрузка требует контролируемого окна и последующей полной сверки; её нельзя назвать атомарной по предположению.

## 4. Конверт события и семантика

```json
{
  "schema_version": "rb.integration.v1-draft",
  "data_mode": "demo",
  "source_system": "demo-1c",
  "source_generation": "demo-gen-1",
  "stream": "sales",
  "event_id": "sale-line-001",
  "revision": 1,
  "operation": "upsert",
  "entity_type": "sale_line",
  "external_id": "sale-line-001",
  "occurred_at": "2026-10-10T10:00:00+07:00",
  "source_recorded_at": "2026-10-10T10:00:05+07:00",
  "exported_at": "2026-10-10T10:01:00+07:00",
  "payload": {
    "point_id": "demo-point-1",
    "menu_item_id": "demo-pancake-1",
    "variant_id": "demo-standard",
    "quantity": "10",
    "unit_id": "portion",
    "recipe_version_id": "demo-recipe-v1",
    "preparation_state": "prepared",
    "modifiers": [],
    "inventory_operation_id": "demo-consumption-001"
  }
}
```

`event_id` в этом варианте — стабильный ID изменяемого логического события, `revision` — монотонная версия. Payload — **полное состояние** этой ревизии, а не прибавка. Если источник выдаёт дельты, адаптер обязан нормализовать их либо согласовать отдельную схему; смешивать варианты нельзя. Идемпотентность inbox: `(source_system, source_generation, stream, event_id, revision)`. Повтор с тем же hash — no-op; тот же ключ с другим hash — конфликт и карантин. Старшая известная ревизия не заменяется поздно пришедшей младшей. Отсутствующие зависимости и необъяснённые пропуски версий — проблема качества.

Отмена/возврат ссылается на исходную строку, количество и причину, содержит `preparation_state`/тип операции. Финансовая коррекция и физический эффект независимы. Нельзя трактовать отрицательную сумму чека как автоматический возврат ингредиентов. `operation=tombstone` снимает актуальность сущности, но не стирает аудит и не отменяет физический расход без соответствующей учётной операции. Перепроведение задаётся новой ревизией и новым соответствующим состоянием эффектов.

Техкарта: ID версии, item/variant/point scope, valid_from/valid_to, время известности, выход порций, строки ingredient/unit/gross/net/loss_semantics, modifiers. Для продажи фиксируется версия, действовавшая на `occurred_at`, или прямо присланная ссылка, если её валидность подтверждена. Расчёт сохраняет использованные коэффициенты. Новый рецепт не переписывает старый расход.

Движение: ID строки документа и revision, тип, location, ingredient/lot/unit/signed_qty, occurred_at/posted_at, статус проведения, ссылки на каноническую физическую операцию и на строки продаж/приёмок с распределёнными количествами. При агрегированном списании за смену необходима точная связь покрытия либо режим без оперативного наложения. Сопоставления по похожим суммам/времени могут быть подсказками для человека, но не основанием автоматического устранения дубля.

## 5. Синхронизация и восстановление

1. Проверить ключ/scopes/capabilities и source_generation. Сохранить договорённую версию схемы и mapping.
2. Получить bootstrap, загрузить все страницы в staging, проверить контрольные суммы, ссылки и полноту. Справочники/единицы/рецептуры применить раньше зависимых продаж. Финальный срез публикуется атомарно для оговорённого scope только после проверки.
3. Зафиксировать boundary_cursor и перейти к изменениям после него. Исторические события, уже включённые в начальный остаток, не проигрываются поверх снимка; их включение должно быть известно из coverage/согласованной границы.
4. Сохранить страницу inbox и `received_cursor` одной транзакцией. Нормализовать/проверить сообщения, затем применить доменные изменения, audit/outbox и `applied_cursor` в транзакции. При карантине оставлять поток/зависимый scope неполным; не публиковать «всё успешно» после пропущенной продажи. Независимые scope могут продолжить обработку.
5. При сбое до commit страница повторяется. При сбое после commit повтор безопасен по уникальным ключам. Временные ошибки сети/429/5xx: ограниченные повторы с exponential backoff+jitter и Retry-After, затем отложенное задание и журнал; не бесконечный цикл.
6. 401/403 — остановка до исправления доступа; 422/неизвестная схема — карантин; 409 конфликт версии; 410 cursor expired — новая согласованная выгрузка и сверка. Полная перезагрузка не складывается со старым ledger; смена поколения источника требует проверки mapping и подтверждения совместимости.
7. Периодическая сверка количества/контрольных сумм документов и остатков, обнаружение пропусков/удалений/поздних исправлений. Частоту согласовать по объёму. Истёкший журнал нельзя компенсировать угадыванием событий.

Журнал ошибки: run, source, stream, entity/event/revision, safe_code, retry_count, first/last_seen, статус и решение, ссылка на защищённый исходный payload. UI показывает **последнюю успешную применённую** синхронизацию по потоку/точке, последнюю попытку и свежесть источника отдельно. Загрузка страницы без применения не обновляет успешную синхронизацию. Для сводного экрана свежесть определяется самым отстающим обязательным источником.

## 6. Сверка снимков и эффектов без двойного учёта

### Каноническая физическая операция

Продажа, расчёт по рецепту и документ списания могут описывать один расход. Они связываются с одним `effect_id`, а не создают три независимых списания. У эффекта есть состояние и ревизии: прогнозный расход по продаже → подтверждённое движение. При расхождении исходное предположение сохраняется в истории, актуальная величина заменяется подтверждённой и создаётся запись расхождения. Одна строка движения может покрывать несколько эффектов с явным распределением, суммы распределений обязаны сходиться. Неоднозначность запрещает автоматическое наложение.

Для одного scope `(location, ingredient, lot-or-unallocated)`:

`Q_operational = Q_snapshot + Σ [E_current(e) - E_included(snapshot, e)]`.

`E_current` — актуальное известное **полное signed-количество** канонического эффекта, уже произошедшего к моменту оперативного расчёта. `E_included` — signed-количество того же эффекта, доказуемо включённое в выбранный снимок. Сумма по объединению известных и включённых эффектов, не по всем версиям подряд. Отсутствие строки покрытия означает 0 только при заявленной полноте coverage; иначе значение неизвестно и формула не применяется. Для включённого исторического эффекта без новых изменений current и included совпадают.

Перед активацией снимка загрузить или восстановить из покрытия соответствующее подтверждённое состояние эффекта: старый расчёт по рецепту не должен переопределять более новое подтверждение 1С. Например, если предварительно рассчитано −300 г, а полный подтверждённый расход равен −310 г, current становится −310 г с записью расхождения, а не создаёт фиктивный возврат +10 г поверх снимка. Для частичного покрытия сохраняется явно неучтённая часть; признак полноты и распределение должны быть в контракте. При отсутствии нужной ревизии/семантики снимок остаётся staging либо публикуется только как подтверждённый остаток без оперативного наложения. Позднейшая доказуемая коррекция после снимка может дать разность; устаревшая оценка — нет.

Курсор доставки означает лишь полученные сообщения. `occurred_at <= snapshot.as_of` **не доказывает** включения: списание может проводиться позже, задним числом или агрегировано. Допустимая альтернатива явному coverage — подтверждённая поставщиком граница полного префикса **учётного** журнала с однозначным mapping всех эффектов; обычный курсор продаж ею не является.

Пример снимка:

```json
{
  "snapshot_id": "demo-snapshot-2",
  "source_generation": "demo-gen-1",
  "consistency_revision": 102,
  "as_of": "2026-10-10T10:05:00+07:00",
  "scope": {"location_id": "demo-point-1"},
  "complete": true,
  "quantity_semantics": "physical_on_hand",
  "coverage_mode": "explicit_effect_quantities",
  "coverage_complete": true,
  "lines": [{"ingredient_id": "demo-ingredient-1", "lot_id": null, "quantity": "700", "unit_id": "g"}],
  "included_effects": [{"effect_id": "demo-consumption-001", "effect_revision": 1, "ingredient_id": "demo-ingredient-1", "lot_id": null, "signed_quantity": "-300", "unit_id": "g"}]
}
```

В большом срезе lines/coverage передаются страницами; публикуются вместе по одному consistency token. Полный снимок не означает автоматически полный coverage — это разные флаги. Отсутствующая строка остатка считается нулём только в явно полном заявленном scope; иначе это неизвестное значение. Snapshot reserves должны быть отдельны от physical_on_hand; если источник отдаёт только available, адаптер обязан раскрыть семантику, чтобы резервы не вычитались повторно.

### Контрольные примеры — синтетические

| Событие | Состояние и расчёт |
|---|---|
| Начальный остаток 1000 г, sale 10 × 30 г ещё не включена | E_current = −300, E_included = 0; оперативно 700 г |
| Повтор той же продажи/ревизии | No-op inbox и effect; остаётся 700 г |
| Снимок 1С 700 г включает расход −300 | 700 + (−300 − (−300)) = 700; повторного списания нет |
| Движение списания −300 приходит после продажи | Связывается с тем же effect_id; не создаёт второе −300 |
| Коррекция расхода до −240 при снимке, включившем −300 | 700 + (−240 − (−300)) = 760 до следующего снимка; коррекция с аудитом |
| Возврат денег за готовые порции | Физический расход не меняется; остаётся 700 в исходном сценарии |
| Снимок 700 г, приняли 100 г из ожидаемых 200 г | Оперативно 800; incoming уменьшается до 100; учётный остаток 1С пока 700 |
| Снимок 1С 800 г включает те же принятые 100 г | 800 + (100 − 100) = 800; поступление не удваивается |

Приёмка имеет локальный receipt_line UUID. Вручную созданный документ 1С связывается по согласованной ссылке/внешнему ID и строкам; при необходимости сотрудник подтверждает mapping. Если 1С принимает только номер документа, требуется проверка уникальности в источнике и периода, а не доверие свободному тексту. Если связь невозможна, показывать приёмку отдельно и не накладывать её на неоднозначный новый снимок.

Снимок принимается только с возрастающей consistency revision в том же source_generation и scope; старый полученный позже хранится для аудита, но не заменяет актуальный. Конкурирующие обработчики используют блокировку scope/optimistic version. Активация снимка, coverage, пересчёт pending effects и обновление projection — единая транзакция. Не завершённый или неоднозначный снимок остаётся staging.

### Что делать при отсутствии доказательств

`coverage_mode=unknown`: показывать последний подтверждённый остаток и отдельные непримирённые операции/оценки расхода. Не вычитать продажи из импортированного остатка автоматически и не добавлять локальную приёмку поверх него. Новая рекомендация использует явно выбранный подтверждённый срез, помечается устаревшей/неполной и требует ручной проверки. Не утверждать, что такой режим обеспечивает оперативное предотвращение дефицита.

Отрицательные значения и расхождения остаются видимыми. Они получают причину: отсутствующая рецептура, единицы, поздний документ, неизвестная связь, недостача, инвентаризация и т. п. Ручное решение сопровождается аудитом, не переписывает исходный факт 1С и не создаёт фиктивный компенсирующий приход.

## 7. Приёмка контракта

До реальной интеграции разработчик 1С и команда подтверждают mapping, значения signed quantities, политику ревизий, состав snapshot coverage, источник recipe version, значения null, правила возвратов, scope ключей, retention журнала и механизм bootstrap. Этап 1 создаёт схемы и demo-fixtures; этап 3 прогоняет те же контрактные тесты на тестовой базе. При несовпадении возможностей обновляется контракт, а не вводятся скрытые предположения.
