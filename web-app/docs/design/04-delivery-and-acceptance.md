# План команды, backlog и критерии готовности

План учитывает ответы: 4–6 начинающих участников, шесть недель, нет доступа к 1С и данным заказчика. Обязательный результат — небольшой автономный **демонстрационный** MVP. Это план работ, а не отчёт об их выполнении. Ни один программный тест, интеграция или модель пока не выполнены.

## 1. Распределение ответственности

| Обозначение | Основная зона | Контроль смежной работы |
|---|---|---|
| У1 | Координатор/backend: каркас, авторизация, БД, Compose, CI, интеграционные схемы | Ревью прав, миграций и контрактов У2 |
| У2 | Учёт, рецептуры, заявки, накладные, приёмки | Ревью численных расчётов У4 |
| У3 | React/TypeScript: основной и адаптивный интерфейс | Проверка UX накладной, ошибок и разграничения доступов |
| У4 | Demo-данные, аналитика, baseline, тестовые сценарии | Контрактные fixtures и сквозная приёмка вместе с У1 |
| У5, если есть | Автотесты, уведомления, резервное копирование, эксплуатация | Снимает часть нагрузки У1/У4 |
| У6, если есть | CatBoost/GRU, внешние demo-адаптеры и исследовательский отчёт | Не меняет учётный код без ревью У2 |

При четырёх участниках задачи У5 делят У1/У4, У6 — У4 с помощью У1. Для минимального релиза сокращается число экранов и внешних подключений, а не проверки целостности. Ежедневно короткая синхронизация; небольшие PR, один проверяющий; общие API-типы и контракт ошибок фиксируются до параллельной реализации. Это распределение человеческой команды, автоматические агенты здесь не запускались.

## 3. Шестинедельный план

| Неделя от старта | Демонстрируемый результат | Контроль объёма |
|---|---|---|
| 1 | Репозиторий, README запуска, миграция, четыре demo-пользователя, два scope точек, каркас экранов, seed, контракт | Проверить ПК/Compose сразу; не строить все сущности целевой модели |
| 2 | Остатки приложения, версии техкарт, demo-продажи, корректный расход, отсутствие дублей, серверные права | Все изменения количества идут через единый доменный сценарий и транзакцию |
| 3 | Заявка → внутреннее уведомление → принятие → накладная → отправка → полная/частичная приёмка; email sink | Это основной вертикальный сценарий; версия документа и конкуренция проверены |
| 4 | Простая аналитика, baseline 1/7/14, корзина с условными ограничениями, печатная накладная, отдельный demo-тест сверки 1С | Не ждать настоящих API, не расширять дизайн до полноценной ERP |
| 5 | Небольшой воспроизводимый CatBoost/GRU-эксперимент, интервалы; demo погоды/новостей/LLM, отказ и бюджетные проверки | Рабочий прогноз остаётся baseline при отсутствии выигрыша; реальные платные подключения не нужны |
| 6 | Заморозка возможностей, исправления, полный сценарий, восстановление из dump, мобильная проверка, инструкция и демонстрация | Новые функции не добавлять; документировать недоделанное вместо заявления полной готовности |

План — ориентир для новичков, не гарантия срока. Если к концу недели 3 цепочка накладной/приёмки не работает, отключить необязательные визуализации и отложить live-внешние адаптеры; исследовательскую часть вынести в небольшой отдельный запуск. Если и он не готов к сдаче, указать невыполненный пункт исходного задания и согласовать перенос, не подменять его сгенерированными метриками.

## 5. Общая готовность задачи

Есть воспроизводимый вход и ожидаемый выход, обработка ошибок, серверная проверка scope, миграция при изменении БД и описание API. Значимые правила проверены unit/integration-тестом; пользовательский путь — сквозным тестом. Секреты не попадают в код, UI и логи. Каждая метрика и выгрузка содержит provenance. Критические изменения количества проходят ревью второго участника. Проверки запускаются на PostgreSQL; удобное ручное демо не заменяет тест конкуренции и повторов.

## 7. Сквозная демонстрация

1. Показать баннер «Демонстрационный режим», собственный ledger, синтетическую точку и остаток 1000 г условного ингредиента. Рецепт: 30 г на порцию.
2. Генератор отправляет продажу 10 порций. Остаток приложения становится 700 г. Повтор той же продажи ничего не меняет.
3. Для будущего окна задан синтетический baseline-расход 1000 г и SS=100 г, incoming=0, срок годности и вместимость допускают заказ. Получается рекомендация 400 г. Указать, что это условные данные, не прогноз по истории заказчика.
4. Сотрудник создаёт заявку; она видна кладовщику нужного склада, появляется in-app уведомление и письмо в локальном sink. Повтор расчёта не создаёт копию заявки.
5. Кладовщик принимает, комплектует, формирует внутреннюю накладную на 400 г и отправляет. Остаток точки по-прежнему 700 г; запас склада уменьшается на отправленное, товар отмечен в пути.
6. Сотрудник подтверждает 250 г по накладной и фиксирует недостачу/ожидание 150 г. Остаток точки 950 г; повтор подтверждения не добавляет ещё 250. Остаток поставки закрывается отдельно либо принимается следующей операцией, статус не становится безусловно «полностью получена».
7. В **отдельном reset-сценарии режима 1С** показать снимок 1000 г → продажа −300 → снимок 700 с coverage; затем приёмка +250 → снимок 950 с coverage. Итог 950 г, а не 1200. Показать последнюю успешную синхронизацию **с demo-адаптером**, а не с реальной 1С. Не переключать источник внутри действующего ledger без процедуры cutover.
8. Показать чужую точку под другим пользователем, отказ погоды/LLM, отрицательный остаток как отдельную проблему и восстановленную копию БД.
9. Открыть отчёт моделей: synthetic provenance, реальные полученные метрики либо «эксперимент ещё не выполнен», сравнение с baseline, группы редких/популярных, ограничения.

## 8. Риски и контрольные решения

| Риск | Решение |
|---|---|
| Нет данных и доступов | Не задерживать demo; этап 3 и доказательство бизнеса явно отложены, источники не выдумывать |
| Слишком большой объём для новичков | Сначала один вертикальный путь накладной; P0 перед P1/P2; полный контракт не реализуется сразу |
| Неизвестный источник реальных продаж | Генератор для demo; реальный учёт продаж только после согласования источника, никаких обещаний автоматического обмена |
| Несовпадение собственного учёта и 1С | Чёткая метка режима, отдельная сверка и процедура перехода; 1С не меняем |
| ПК выключен/сломался | Постоянный серверный ПК, копия на другом носителе, проверка восстановления; браузер не хранит единственную копию |
| Неизвестные логистические ограничения | Только условные demo-параметры; реальные рекомендации требуют подтверждения данных кладовщиком |
| Ложная уверенность от синтетических метрик | Отдельный provenance во всех отчётах; генератор не является доказательством бизнеса |

Для будущего обращения к заказчику достаточно сначала запросить обезличенный словарь и примеры структуры, а не полную базу. Если отказ сохраняется, итог проекта остаётся честно обозначенным учебным прототипом. Это не мешает защитить архитектуру и работающий сценарий, но ограничивает заявления о готовности реального внедрения.
