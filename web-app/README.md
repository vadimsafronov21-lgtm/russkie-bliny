# Русские блины · первый работающий этап

Автономный **демонстрационный** стенд. Здесь нет данных заказчика и соединения с реальной 1С. Все меню, продажи, рецептуры, начальные остатки и накладные синтетические. Приложение ведёт собственный журнал; остатки не называются сверенными с 1С.

## Что работает

- Вход по логину/паролю, четыре роли и серверные ограничения по точкам. Два отдельных аккаунта сотрудников позволяют проверить изоляцию данных.
- Русский интерфейс: обзор, остатки, заявки и внутренние накладные, аналитика, прогноз, журнал действий, уведомления. Адаптивный режим проверяется на телефоне шириной 390 px.
- Заявка → принятие с резервированием склада → комплектация и накладная → отправка → частичная/полная приёмка. Накладную можно напечатать из браузера.
- Склад уменьшается при отправке; точка увеличивается только на принятое количество. Повторные команды защищены ключами идемпотентности, изменения документа — проверкой версии.
- Демонстрационная продажа списывает ингредиенты по действовавшей рецептуре. В API предусмотрены отмена до приготовления и финансовый возврат готового блюда без восстановления сырья. История расхода сохраняет версию техкарты.
- Аналитика синтетических продаж; пропуск данных не подменяется нулём. Правила внимания пока фиксированы и описаны в UI.
- Baseline: среднее до четырёх предшествующих одноимённых дней недели, горизонты 1/7/14. Три временных блока проверки, MAE/WAPE/Bias. Учитывается дата доступности сведений, а не только дата продажи. Эмпирический интервал есть только для первого дня; его покрытие пока не измерено.
- Черновая потребность учитывает расход всех блюд, остаток, условный страховой запас, упаковку и ещё не принятую подтверждённую поставку. Сроки годности, вместимость и реальные сроки доставки **не проверяются** — обязательна ручная проверка.
- Транзакционная внутренняя лента/outbox, отдельный worker, попытки и ошибки email. По умолчанию письма сохраняются локально как `.eml`; реальным людям ничего не отправляется.
- Alembic, OpenAPI, зафиксированные зависимости, локальная резервная копия и проверка её восстановления.

Это реализация основного вертикального сценария, а не завершение всех требований исходного проекта. Подробные границы: [текущий статус](docs/STATUS.md). Проектирование: [проектная основа](docs/design/README.md).

Проверено 16 серверных и 2 браузерных сценария; восстановление SQLite-копии проверено по 18 таблицам. Подробности и ограничения: [протокол проверки](docs/VERIFICATION.md).

## Локальный запуск на этом ПК

Рабочая папка: `E:\CodexProjects\russkie-bliny-app`. В ней уже подготовлены `.venv`, зависимости frontend и сборка `frontend/dist`. Docker на этом ПК не обнаружен; локальный просмотр использует SQLite. Это не подтверждает корректность работы под PostgreSQL.

В PowerShell из папки проекта:

```powershell
.\scripts\start-local.ps1
```

Открыть [приложение](http://127.0.0.1:8000) и [API-документацию](http://127.0.0.1:8000/docs). Скрипт применяет миграции, создаёт demo-данные при первом запуске и запускает сервер. Остановка — Ctrl+C. Существующая БД не очищается. Для другого порта: `-Port 8001`.

Обработчик уведомлений в отдельном терминале:

```powershell
.\.venv\Scripts\python.exe -m backend.app.worker
```

Письма появляются в `data/mail`. Это локальная имитация доставки, не доказательство получения письма адресатом. SMTP можно настроить переменными окружения, но эта demo-версия намеренно использует получателя `notifications@bliny.invalid`.

## Установка на чистой машине

Нужны Python 3.13, Node.js 24 и pnpm 11.25.0. Из корня проекта:

```powershell
py -3.13 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
corepack enable
corepack prepare pnpm@11.25.0 --activate
Set-Location frontend
pnpm install --frozen-lockfile
pnpm run build
Set-Location ..
.\scripts\start-local.ps1
```

Если Python в локальном окружении создан, но `ensurepip` не сработал, установку можно выполнить через доступный глобальный pip: `python -m pip --python .venv\Scripts\python.exe install pip -r requirements.txt`. На текущем ПК pnpm доступен по пути `C:\Users\Sergey Samsonov\.cache\codex-runtimes\codex-primary-runtime\dependencies\bin\fallback\pnpm.cmd`; обычная установка pnpm на другом ПК этого пути не требует.

Для разработки запустить backend указанной командой, а во втором терминале из `frontend` — `pnpm dev`. Vite проксирует `/api` на порт 8000. Для единого локального сервера после изменений frontend заново выполнить `pnpm run build`.

Конфигурация читается из **окружения процесса**. Нативный Python не подхватывает `.env` автоматически: в PowerShell задавайте `$env:NAME='value'`. Docker Compose читает `.env` для подстановок. `.env.example` содержит только демонстрационные значения и примеры, а `.env` исключён из Git.

## Docker Compose и PostgreSQL

Подготовлен вариант с PostgreSQL, API/frontend и worker. Из корня проекта:

```powershell
docker compose up --build -d
docker compose logs -f api worker
```

Порт 8000 опубликован только на `127.0.0.1`, БД не публикует порт наружу. Образы запускают миграции и seed; worker ждёт готовности API. По умолчанию email идёт в локальный sink внутри volume `app_data`.

Compose и PostgreSQL на текущем ПК **не запускались**: Docker/PostgreSQL отсутствуют. В CI подготовлены тесты на PostgreSQL 17, но удалённый CI пока не запускался. До сетевого/пилотного использования нужны проверка этого варианта, отдельные пароли, TLS, `COOKIE_SECURE=true`, реальные ограничения и эксплуатационные настройки. Нельзя просто открыть этот учебный стенд с известными паролями в интернет.

## Проверка

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m ruff check backend tests scripts
.\.venv\Scripts\python.exe -m alembic check
Set-Location frontend
pnpm run build
pnpm exec playwright install chromium
pnpm exec playwright test
```

Перед браузерными тестами сервер должен работать. Они изменяют только demo-данные: создают заявку, отправляют её и принимают двумя частями. Если Chromium не установлен, на Windows можно использовать Edge: `$env:BROWSER_EXECUTABLE='C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe'`.

Серверные тесты создают отдельную временную SQLite БД. Для PostgreSQL переменная `TEST_DATABASE_URL` должна указывать на **отдельную расходную тестовую БД с именем, оканчивающимся на `_test`**: тесты удаляют созданные таблицы при завершении. Не передавайте туда рабочую БД. В ограниченном окружении задавайте доступную временную папку pytest через `--basetemp` внутри `.cache`; папка должна быть специально выделена для тестов.

## Резервная копия и восстановление

Для локальной SQLite используется backup API, а не копирование открытого файла:

```powershell
.\.venv\Scripts\python.exe scripts/backup-local.py
.\.venv\Scripts\python.exe scripts/verify-backup.py
```

Первая команда сохраняет отдельный файл в `backups`. Вторая восстанавливает последнюю копию в новый файл `.cache/restored-*.db`, проверяет целостность, внешние ключи, количество и хеш содержимого каждой таблицы. Рабочая БД не заменяется. Отчёт: `docs/backup-verification.json`. Чтобы открыть восстановленную копию отдельно, задайте `DATABASE_URL=sqlite:///полный/путь/к/restored.db` и запустите второй сервер на другом порту.

Для PostgreSQL (после проверки Compose) выполнять dump внутри контейнера, чтобы не повредить двоичный архив перенаправлением PowerShell:

```powershell
docker compose exec db pg_dump -U bliny -d bliny -Fc -f /backups/bliny-demo.dump
docker compose exec db createdb -U bliny bliny_restore_test
docker compose exec db pg_restore -U bliny -d bliny_restore_test --no-owner /backups/bliny-demo.dump
```

Используйте уникальное имя архива при регулярных копиях. Затем сверить таблицы и пользовательский сценарий в восстановленной БД. Эти PostgreSQL-команды здесь пока не проверены. Копию нужно хранить и на отдельном носителе: копия на том же диске не защищает от его поломки. Планировщик ежедневных backup ещё не настроен; Word/Excel-экспорт не заменяет backup БД.
