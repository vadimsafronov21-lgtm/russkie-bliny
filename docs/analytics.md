# Работа аналитиков

Расчёты расположены в `src/blini/data.py`, `forecast.py`, `inventory.py`, `service.py`. Они не знают о Qt, SQLite и файлах интерфейса. pandas-таблицы передаются явно; функции расчётов не меняют входные таблицы. `service.run_pipeline(raw, as_of, Config)` — единая точка для ноутбука, CLI и окна.

## Прогноз

`METHODS` — реестр функций `(history: pd.Series, dates: DatetimeIndex, config: Config) -> pd.Series`. Series истории имеет индекс календарных дат до даты происхождения прогноза; неизвестные/закрытые дни NaN. Ответ индексируется запрошенными датами, содержит неотрицательные порции, NaN для неизвестного. Добавьте функцию и запись в METHODS; расширьте Config, если нужны параметры. Остальные модули менять не требуется. Метод должен использовать только переданную историю, без доступа к полному набору/глобальным данным.

Сезонный наивный: D-7. Для горизонта длиннее 7 дней последняя историческая неделя повторяется, без обращения к будущим фактам. Среднее по дню недели: известные значения соответствующего дня последних `weekday_mean_weeks` календарных недель. Закрытые дни не уменьшают среднее открытых дней.

Три блока по семь дней заканчиваются на as_of. Для каждого origin обучение строго <=origin, контроль — следующие семь дней. Минимальная длина обучающего календарного отрезка — 14 дней. Метрики считаются на одинаковых известных датах всех сравниваемых алгоритмов; `n` и `folds` показывают фактическое покрытие. Выбор наименьшего pooled MAE (в порциях); при равенстве порядок по имени метода. WAPE = сумма абсолютных ошибок / сумма фактов, при сумме фактов 0 — None. Ошибки каждого дня и origin доступны в Report.errors, признак eligible сообщает участие в сравнении.

При менее чем `min_eval_points` общих контрольных точек применяется среднее последних `fallback_observations` известных открытых дней. Если у выбранного метода нет наблюдения для отдельных дней, для этих дней также используется резервное среднее. Каждый такой случай подписан в forecast.explanation/method. Блюдо вообще без истории имеет неизвестный прогноз; автоматическая закупка затронутых ингредиентов блокируется, остальные могут рассчитываться.

Использование одних контрольных блоков и для выбора, и для показа метрик может давать оптимистичную оценку выбранного метода. Для итогового исследования выделите дополнительный нетронутый контрольный период. Параметры первого прототипа задаются заранее; их подгонка на тестовых датах не производится.

## Закупки

`ingredient_demand(forecast, recipes)` возвращает дневную потребность; неизвестный спрос сохраняется в сумме, а не игнорируется. `simulate(demand, stock, deliveries, order=None)` возвращает дневной журнал и оставшиеся партии. FEFO сортирует по сроку и затем ID партии. Дефицит — потерянный расход, не отрицательный остаток.

`safety_stock(total_demand, config)` — место замены процентного правила (сейчас 15% потребности L+R). `recommend_orders(...)` — место изменения политики закупок. Конфигурация общих методов — `config/default.json`; сроки, упаковки и пересмотр индивидуальны в purchase_params.csv.

Утро заказа = as_of+1. Поступление = утро заказа + L. Период защиты включает L+R дней, заканчивается за день до следующей плановой поставки при том же сроке. Если L+R >7, отдельно создаётся расширенный planning_forecast (до max_plan_days); пользовательский forecast остаётся семидневным.

Сначала симулируется отсутствие нового заказа. Суммируется дефицит после даты возможного прихода; до этой даты выводится отдельное предупреждение. К позднему дефициту добавляется max(0, страховой запас − остаток, годный после конца периода). Полученное значение ограничивается снизу минимальным заказом и округляется вверх до упаковки. При нулевой потребности заказа минимум не применяется. Затем повторяется дневная симуляция **с рекомендованной партией** и проверяются остаточный дефицит, недостигнутый буфер и риск списаний.

Это прозрачная эвристика одной поставки, не оптимизатор стоимости/числа партий. При короткой годности рекомендация может требовать нескольких поставок; приложение сохраняет предупреждение и показывает неподкрытый спрос. Финальную закупку человек корректирует с поставщиком.

## Основные выходы

| Функция | Выход |
|---|---|
| validate_data | нормализованные таблицы, errors и warnings; require_valid поднимает ValueError |
| forecast_sales | дневной прогноз, сводные метрики, дневные ошибки |
| ingredient_demand | date, store_id, ingredient_id, quantity |
| simulate | журнал demand/arrivals/expired/consumed/shortage/remaining и партии |
| recommend_orders | численные компоненты, даты, заказ, статус, warning, explanation; журнал baseline/with_order |
| run_pipeline | Report со всеми перечисленными таблицами; export пишет CSV |

Критические тесты — `tests/test_core.py`. Для нового метода добавьте проверку доступа только к train и пример известного ожидаемого результата. Ноутбук не должен дублировать формулы основных методов.
